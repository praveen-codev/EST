# Neon track registry

EST uses separate Neon projects so real production feedback cannot be changed by sandbox
experiments.

| Track | Project | Project ID | Default branch |
|---|---|---|---|
| Production | `Codev-EST-prod` | `fragrant-cloud-37068465` | `production` |
| Sandbox | `Codev-EST-sandbox` | `flat-breeze-15814484` | `sandbox` |
| Archive | `Codev-EST-archive` | `dry-cloud-96538248` | `archive` |

Project IDs are identifiers, not credentials. Connection strings stay in ignored local env files or
the deployment secret store.

## Local environment files

The current checkout uses:

```text
.env.local          production
.env.sandbox.local  sandbox
.env.archive.local  archive administration only
```

All three names are covered by the repository's `.env.*` ignore rule.

The Devin App launcher accepts the desired file:

```bash
EST_ENV_FILE="$PWD/.env.sandbox.local" \
EST_TRACK=sandbox \
EST_CALENDAR_SYNC_ENABLED=false \
npm start
```

The `sandbox` profile uses real Google sign-in, so its deployment still needs the normal
`GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Calendar linking remains disabled.

## Track rules

### Production

- Owns real Google calendar refresh tokens and sync cursors.
- Owns authoritative candidates, suggestions, sessions, feedback, catalogs, and reports.
- Is the only user-facing track allowed to link or directly synchronize calendars.

### Sandbox

- Uses real Google sign-in, but does not link calendars or store Google calendar refresh tokens.
- Receives canonical calendar evidence through the external distributor.
- Owns all experimental decisions, sessions, feedback, catalogs, hashtags, and reports.
- Never writes back to production.

### Archive

- Has no EST web/API deployment.
- Receives only versioned, redacted, checksum-verified evidence from the archive job.
- Is not in the normal request path.

## Calendar distributor contract

The external scheduled design fetches Google once using production credentials, then independently
delivers a versioned evidence envelope to production and sandbox. Each target records its own
outcome so one failure does not roll back the other.

Cross-track identity uses Google subject and normalized email. Database IDs remain local to each
track: a member who signed in to sandbox before replication keeps their sandbox ID, and copied
identities, events and attendees are rewritten to it. A production member whose subject and e-mail
resolve to different sandbox members (or whose e-mail belongs to another Google account) is
skipped and reported as `member_conflicts`.

Each database records its track in `deployment_track` on first start. The distributor refuses a
source that is not production or a target that is not sandbox, and claims an unclaimed target as
sandbox.

The distributor may copy:

- Organization and member identity keys needed to resolve the owner.
- Tokenless identity metadata.
- Calendar event evidence and attendees.
- Sync and replication metadata.
- A fresh candidate/suggestion baseline generated by the sandbox engine from the copied evidence
  when sandbox has no candidate for the event; changed evidence is re-analysed in sandbox.

The current distributor deliberately omits encrypted tokens, sync cursors, provider error text, and
the raw provider JSON payload.

It must not copy:

- OAuth refresh or access tokens.
- Refresh-token families.
- Production sessions or feedback.
- Candidate or suggestion decisions.
- Catalog or hashtag edits.
- Audit records.

## Commands

Apply the archive-only schema:

```bash
infra/neon/migrate-archive.sh
```

Preview a production-to-sandbox replication:

```bash
infra/neon/replicate-calendar-evidence.sh
```

Apply it:

```bash
EST_REPLICATION_DRY_RUN=false infra/neon/replicate-calendar-evidence.sh
```

The default evidence window includes events ending in the previous 30 days or later. Override it
with `EST_REPLICATION_LOOKBACK_DAYS`.

## Scheduled jobs

Unattended work runs outside the API, from an external scheduler (a Devin Automation every 12
hours). Both jobs start from the API boot jar through `infra/neon/run-job.sh`, read configuration
only from the environment, need Java 25 on `PATH` or in `JAVA_HOME` (SDKMAN is only a fallback),
never run Flyway, serve no traffic, and print one counts-only line.

### Protected secrets

| Name | Used by | Value |
|---|---|---|
| `EST_PROD_DATABASE_URL` | calendar sync | Direct `postgres://` URL for the production sync role |
| `EST_CRYPTO_KEY` | calendar sync | The production refresh-token key; must equal the API's key |
| `GOOGLE_CLIENT_ID` | calendar sync | Production OAuth client ID |
| `GOOGLE_CLIENT_SECRET` | calendar sync | Production OAuth client secret |
| `EST_SOURCE_DATABASE_URL` | replication | Direct `postgres://` URL for the read-only production role |
| `EST_SANDBOX_DATABASE_URL` | replication | Direct `postgres://` URL for the sandbox writer role |

Non-secret settings: `EST_REPLICATION_DRY_RUN` (defaults to `true`; the schedule sets `false`),
`EST_SYNC_ORG`, `EST_REPLICATION_ORG`, `EST_REPLICATION_LOOKBACK_DAYS`, `EST_JOB_JAR`. URLs default
to `sslmode=require`.

### Database roles

The jobs add defence in depth. They don't replace least-privilege roles, which an operator must
create:

- **Production sync role.** `CONNECT`, schema `USAGE`, and `SELECT`, `INSERT`, `UPDATE`, `DELETE` on
  the application tables. Read-only access to `flyway_schema_history` and `deployment_track`. No
  `CREATE` or ownership: migrations stay with the API release role.
- **Production read-only role** for the replication source. `CONNECT`, schema `USAGE`, and `SELECT`
  on the application tables, `flyway_schema_history`, and `deployment_track`. No write or DDL
  privilege. Also set `ALTER ROLE ... SET default_transaction_read_only = on`.
- **Sandbox writer role.** `CONNECT`, schema `USAGE`, and `SELECT`, `INSERT`, `UPDATE`, `DELETE` on
  the sandbox application tables, plus `INSERT` on `deployment_track` for the first claim. No DDL.

### Safety checks

- **Calendar sync** (`infra/neon/sync-calendars.sh`, main class `CalendarSyncJob`).
  - The run is refused unless the profile is `prod` with calendar sync enabled and mock Google off.
  - The database must already be claimed as `prod`. The job never claims a track.
  - The database must carry exactly this build's versioned migrations.
  - Each active identity syncs in its own transaction. That transaction holds the identity's
    `member_identities` row lock (`FOR UPDATE SKIP LOCKED`), the same lock the API's manual sync
    takes. While one sync holds it, the other skips that identity and reports it as `busy`.
  - A failure affects only its own identity and is recorded in `calendar_sync_runs`.
- **Replication** (`infra/neon/replicate-calendar-evidence.sh`).
  - Source and target must be different databases.
  - The source must be `prod` and the target `sandbox` (an unclaimed sandbox is claimed).
  - Both must carry exactly this build's versioned migrations.
  - The source connection runs with `readOnlyMode=always` and holds one `REPEATABLE READ READ ONLY`
    transaction, checked through `transaction_read_only`.
  - A transaction-scoped advisory lock on the sandbox lets only one replication write at a time.
  - Dry run rolls the sandbox transaction back.

### Exit codes

`0` ok · `1` error (configuration or connectivity; only the exception type is printed) · `2` refused
by a safety check · `3` sync finished but some identities failed · `4` another replication holds the
lock.

### Automation command sequence

```bash
cd backend && ./gradlew bootJar --no-daemon -q && cd ..
export EST_JOB_JAR="$(ls backend/build/libs/est-api-*.jar | grep -v -- -plain)"
infra/neon/sync-calendars.sh; sync=$?
[ "$sync" -eq 0 ] || [ "$sync" -eq 3 ] || exit "$sync"
EST_REPLICATION_DRY_RUN=false infra/neon/replicate-calendar-evidence.sh; repl=$?
[ "$repl" -eq 0 ] || [ "$repl" -eq 4 ] || exit "$repl"
exit "$sync"
```

A busy replication (`4`) is retried by the next run. A partial sync (`3`) still replicates the
evidence that did sync, then fails the run so someone looks at `calendar_sync_runs`.

## Migrations

- Production and sandbox use the normal EST Flyway migrations.
- Archive uses archive-only Flyway migrations.
- Application traffic uses pooled connections.
- Flyway, dumps, and replication use direct connections.
- Test every migration on an isolated Neon branch before applying it to production.
