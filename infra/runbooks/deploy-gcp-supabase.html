Enablement Session Tracker — first deployment

Google Cloud Run (API + web) · Supabase Postgres (database) · Google sign-in and Calendar. Written for someone who has never deployed before: every step says where to do it, what to do, and how to check it worked.

How to read this page

Terminal= the Terminal app on your Mac (⌘Space, type Terminal). Commands are run from the project folder unless said otherwise.
Browser= a web console you click through (Google Cloud, Supabase, your domain provider).
Wait= nothing to do but wait for something to finish.

Every command block has a Copy button. Paste into Terminal with ⌘V and press Return. Text shown in orange is a value you replace with your own. Green Verify boxes tell you exactly what "working" looks like; don't move on until you see it.

Most steps are one script in infra/deploy/. The scripts read a single settings file (~/est-deploy.env), refuse to run if a value is missing, do nothing harmful when re-run, and end with their own checks. If a script prints a line starting with ✖, read it — it says what to fix.

What you need before starting

A Mac with the project cloned (the folder that contains web/, backend/, infra/).
Docker Desktop installed and running (whale icon in the menu bar).
A Google account that can create a Google Cloud project and attach a billing account (or someone who can do that for you once).
A Supabase account (free tier is fine to start).
Optional: a domain you control (for example acme.com). Not required — see the two paths below.

If you go for Path B, the web app and the API must live under the same domain (app.acme.com + api.acme.com). The login cookie is deliberately strict and is only sent between names on the same domain. Two different free addresses (e.g. …run.app for the API and …vercel.app for the web) would log everyone out on every page refresh — that is exactly what Path A's proxy avoids.

Total time the first time: Path A about 45–60 minutes; Path B 60–90 minutes, of which ~30 is waiting for DNS and certificates.

Create the settings file

Terminal5 min

All scripts read one file in your home folder: ~/est-deploy.env. You will fill it in gradually as you collect values in the next steps. Create it from the template now:

cd /path/to/EST          # the project folder; e.g. ~/Documents/work/repos/EST
cp infra/deploy/est-deploy.env.example ~/est-deploy.env
open -e ~/est-deploy.env      # opens it in TextEdit

Fill in the Google Cloud, Addresses and who may sign in sections now (you choose these yourself). Leave the Supabase and Google OAuth lines for later steps. Rules: no spaces around =, no quotes needed, lines starting with # are comments.

SettingWhat to putExample
PROJECT_IDA new, globally unique id for your Google Cloud project: lowercase letters, digits, dashes, 6–30 charsest-prod-acme
REGIONThe Cloud Run region closest to your userseurope-west1, us-central1, asia-south1
DOMAIN_MODEnone for Path A (free, no domain) or custom for Path Bnone
DOMAINPath B only: your domainacme.com
WEB_HOST / API_HOSTPath B only: the two names you will create under it (ignored on Path A)app.acme.com / api.acme.com
ALLOWED_DOMAINSEmail domains allowed to sign in (comma-separated)acme.com
BOOTSTRAP_ADMINSYour email(s) — become admins automatically on first sign-inyou@acme.com
In TextEdit the file shows your values and the Supabase/Google lines still say change-me. Save with ⌘S. Keep this file private — it will hold passwords.

Install tools and log in to Google Cloud

Terminal10 min

Install the Google Cloud command-line tool (one time). If you don't have Homebrew, follow cloud.google.com/sdk/docs/install instead.

brew install --cask google-cloud-sdk
gcloud components install beta --quiet

Log in. A browser window opens — pick the Google account that will own the project.

gcloud auth login

Now run the first check script. It confirms Docker is running, you are logged in, and your settings file has the basics.

infra/deploy/00-check-tools.sh
Four ✔ lines: gcloud version + your account, Docker running, settings file OK. If you see ✖, it tells you what is missing (e.g. "Docker Desktop is not running").

Google Cloud project

BrowserTerminal10 min

3a. Create the project and attach billing

  1. Open console.cloud.google.com/projectcreate.
  2. Project name: Enablement Session Tracker. Click Edit next to the generated id and set it to exactly your PROJECT_ID from the settings file. Click Create.
  3. Open Billing → Account management, select your new project and link a billing account. (Cloud Run has a generous free tier; expect a few dollars a month for one always-on small instance.)
At Billing → My projects your project shows a billing account, not "Billing is disabled".

3b. Turn on the services EST uses

infra/deploy/01-gcp-project.sh

This enables Cloud Run, Artifact Registry (image storage), Secret Manager, Cloud Build and the Calendar API; creates the image repository est; creates the identity the API runs as. Takes 1–2 minutes.

The script ends with ✔ lines and a link. Open it: the Artifact Registry page lists a repository named est in your region.
What the script runs (for the curious) 
gcloud config set project PROJECT_ID
gcloud services enable run.googleapis.com artifactregistry.googleapis.com secretmanager.googleapis.com cloudbuild.googleapis.com calendar-json.googleapis.com iamcredentials.googleapis.com
gcloud artifacts repositories create est --repository-format=docker --location=REGION
gcloud auth configure-docker REGION-docker.pkg.dev
gcloud iam service-accounts create est-api --display-name="EST API runtime"

Supabase database

Browser10 min

EST uses Supabase only as a PostgreSQL database. You will not use Supabase Auth, its API keys or its table editor.

  1. Go to supabase.com/dashboard → New project.
  2. Name: est. Region: the one closest to your REGION (e.g. Cloud Run europe-west1 → Supabase West EU (Ireland)).
  3. Database password: click Generate a password, then copy it into your settings file as SUPABASE_DB_PASSWORD right away — Supabase will not show it again.
  4. Click Create new project and wait ~2 minutes until the project says Active.
  5. Open Project Settings (gear icon, bottom left) → Database. Find Connection string and switch the method to "Session pooler" (not Direct connection, not Transaction pooler).
  6. From the shown string, copy two things into your settings file:
    • SUPABASE_POOLER_HOST = the host, looks like aws-0-eu-west-1.pooler.supabase.com
    • SUPABASE_PROJECT_REF = the 20 characters after postgres. in the user name (also visible in your dashboard URL)
Why the Session pooler: Google Cloud Run talks IPv4 only, and Supabase's Direct connection is IPv6-only on the free tier (it would simply never connect). The Transaction pooler (port 6543) breaks the Java database driver. The Session pooler on port 5432 is the one that works.

Optional but recommended, defence in depth: Project Settings → API → Exposed schemas: remove public. EST keeps all its tables in its own schema est, which Supabase never exposes to the internet anyway.

Your settings file now has SUPABASE_PROJECT_REF, SUPABASE_POOLER_HOST and SUPABASE_DB_PASSWORD filled in, none saying change-me. Quick connectivity test from Terminal (replace the orange host with yours): 
nc -zv aws-0-eu-west-1.pooler.supabase.com 5432
Expected: Connection to … port 5432 [tcp/postgresql] succeeded!

Google sign-in (OAuth client)

Browser10 min

This is what lets people sign in with their Google account and lets EST read their calendars (read-only). You create it once in your Google Cloud project.

5a. Consent screen

  1. Open Google Auth Platform → Overview (make sure your project is selected at the top) → Get started.
  2. App name: Enablement Session Tracker. User support email: yours.
  3. Audience: choose Internal if your company uses Google Workspace on this domain (recommended — no review needed). Otherwise External.
  4. Contact information: your email. Agree, Create.
  5. Left menu → Data access → Add or remove scopes. Tick: …/auth/userinfo.email, …/auth/userinfo.profile, openid, and under Google Calendar API: …/auth/calendar.readonly and …/auth/calendar.events.readonly. Update, then Save.
  6. If you chose External: left menu → Audience → under Test users add every colleague's email. While the app is in Testing, only these people can link their calendar. (Publishing to everyone requires Google's verification because calendar access is a sensitive scope.)

5b. The OAuth client

  1. Left menu → Clients → Create client.
  2. Application type: Web application. Name: est-api.
  3. Path B only — Authorised JavaScript origins → Add URI: https://app.acme.com (your WEB_HOST, with https://, no trailing slash). Authorised redirect URIs → Add URI: https://api.acme.com/api/v1/calendar/identities/link/callback.
    Path A: leave both lists empty for now — you will add your …run.app address in Step 9 once you know it.
  4. Create. A dialog shows the Client ID and Client secret. Copy both into the settings file as GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET.
Settings file: GOOGLE_CLIENT_ID ends with .apps.googleusercontent.com; GOOGLE_CLIENT_SECRET starts with GOCSPX-. Path B: in the console the client est-api shows one origin and one redirect URI exactly matching your two hostnames.

Store the secrets

Terminal3 min

The script generates the app's own signing keys (for login tokens) and encryption key (for stored calendar access), and puts them together with your Supabase password and Google client secret into Secret Manager. The API reads them from there — nothing secret is ever typed into Cloud Run by hand.

infra/deploy/02-secrets.sh
Five ✔ "Created secret est-…" lines and "API runtime identity may read all five secrets". Open Secret Manager: est-jwt-private-key, est-jwt-public-key, est-crypto-key, est-db-password, est-google-client-secret.

Re-running the script later only updates the Supabase password and Google secret; the signing/encryption keys are kept (changing them would log everyone out and require re-linking calendars).

Build and upload the app

TerminalWait5–10 min

Builds two container images on your Mac — the API (Java) and the web app — and uploads them to your Artifact Registry. The web image has the API's address baked in, so the order differs by path:

Path A (no domain) — the API must exist first so its address can be built into the web app. Run the API deploy now (it builds and pushes the API image itself), then build:

infra/deploy/04-deploy-api.sh && infra/deploy/03-build-push.sh

Path B (own domain) — the addresses are known up front:

infra/deploy/03-build-push.sh
Two "✔ Pushed …/est-api:<tag>" / "…/est-web:<tag>" lines. On Path A the API deploy also printed "✔ API is UP" and a note that it used a placeholder web address for now — expected. The Artifact Registry page shows both images.

Deploy the API

TerminalWait3 min

Path A: you already did this in Step 7 — skip to Step 9. Path B:

infra/deploy/04-deploy-api.sh

This creates the Cloud Run service est-api with all its settings and secret references, keeps exactly one instance always on (the calendar sync runs inside it every 15 minutes), waits for it to start, and checks its health. On first start the API creates the database schema est in Supabase and applies its 3 migrations.

"✔ API is UP and connected to Supabase", "✔ Production flags: devMode=false…", and a "✔ Flyway: Successfully applied 3 migrations" line. In Supabase → Table Editor, switch the schema dropdown (top left) from public to est: you see tables like members, sessions, catalog_items.
If it says the API is not healthy, run the log command it prints. The most common causes are in Troubleshooting (wrong pooler host, wrong password, missing Google client id).

Deploy the web app

TerminalBrowser (Path A)5 min
infra/deploy/05-deploy-web.sh

Path A — the script prints your app's address (https://est-web-….run.app). Two more things:

  1. Tell the API about that address (sign-in origin and Google redirect) by deploying it once more: 
    infra/deploy/04-deploy-api.sh
  2. Add the address to the OAuth client: Google Auth Platform → Clients → est-api → Authorised JavaScript origins: https://est-web-abc123-ew.a.run.app and Authorised redirect URIs: https://est-web-abc123-ew.a.run.app/api/v1/calendar/identities/link/callback (the script prints both lines ready to paste) → Save. Then skip Step 10.
Path A: the second API deploy ends with "✔ API now trusts the web address https://est-web-…". Path B: "✔ Web is serving. Temporary address: …run.app" — opening it shows the sign-in page, but do not sign in yet; it only works once your own domain is attached (next step).

Point your domain at it (Path B only)

TerminalBrowser (your domain provider)Wait10 min + waiting

Path A: nothing to do here (the script just confirms that). Path B: tell Cloud Run which hostnames belong to which service, then create the DNS records it asks for.

infra/deploy/06-domains.sh

The script prints a small table with two records, typically:

api.acme.com   CNAME   ghs.googlehosted.com.
app.acme.com   CNAME   ghs.googlehosted.com.

Now in your domain provider's DNS page (Cloudflare, GoDaddy, Namecheap, Route 53, …) add exactly those records. Common gotchas:

  • In the Name/Host field most providers want only the part before your domain: api and app, not the full name.
  • If your provider is Cloudflare, set the proxy status to DNS only (grey cloud), not proxied, or the certificate step will fail.
  • If the script printed A/AAAA records instead of a CNAME (this happens for a bare domain), create all of them.
Wait 5–30 minutes, then run the verification in the next step. You can watch certificate progress in Cloud Run → Domain mappings — both rows turn to a green check.

Verify everything

Terminal1 min, repeat as needed
infra/deploy/07-verify.sh
All lines ✔: (Path B) DNS resolves for both names and certificates are ready; API health UP, the API knows your Google client id, protected routes answer 401, developer endpoints answer 404, the sign-in page loads, and (Path A) the API no longer holds the placeholder web address. The last line says All checks passed. Any ✖ about DNS or certificates just means "wait a bit longer" — re-run the script.

First sign-in and smoke test

Browser5 min
  1. Open your app — Path A: the https://est-web-….run.app address, Path B: https://app.acme.com → Sign in with Google using one of your BOOTSTRAP_ADMINS addresses. You land on Today and the Admin item in the left rail is enabled — you are an admin.
  2. Account menu (top right) → Linked calendars → Add Google account. Google asks for consent (read-only calendar). After consenting you return to the page with a "Calendar linked" message and the first import has already run.
  3. Add a second Google account the same way if you have one — this is the "partner accounts" feature.
  4. Click Sync calendar in the top bar twice. The second time it reports unchanged events and creates no duplicates.
  5. Go to Inbox and Today: your real meetings that match the team's session formats (101, 201, pair programming, AMA, sprint in a day) appear as candidates.
  6. Ask a colleague on an allowed domain to sign in: they see "Waiting for approval". In Admin you approve them (or call PATCH /api/v1/admin/members/{id} with {"status":"ACTIVE"}).
After a page refresh you are still signed in (this proves the same-domain cookie works). Linked calendars shows your account as active with a "last sync" time.
Path B only: if refreshing the page sends you back to sign-in, the web and API hostnames are not on the same domain, or you opened the temporary …run.app address instead of https://app.your-domain.

Free domain options (only if you want Path B)

Short version: nobody gives away real domains for free any more (Freenom, the old .tk/.ml/.ga source, shut down), and Cloudflare does not offer free domains — its registrar sells them at cost (about $10/yr for .com) and its free products (pages.dev, workers.dev) cannot point at Cloud Run. What exists for $0 are free sub-domains of someone else's domain. Any of these works for Path B as long as you can create CNAME records for app.… and api.….

OptionYou getWorks with Cloud Run?Catch
Path A (this guide)est-web-….run.app from GoogleYes — no DNS at allUgly address; otherwise none. Recommended.
FreeDNS (afraid.org)yourname.mooo.com, …chickenkiller.com, dozens of shared domains; create app.yourname.mooo.com and api.yourname.mooo.com as two recordsYes — supports CNAME/TXT, changes are live immediatelyShared domains have a spammy reputation; some are on blocklists. Free tier limited to a handful of records.
is-a.devyourname.is-a.dev plus nested app.yourname.is-a.dev / api.yourname.is-a.dev (one JSON file each, via GitHub pull request)Yes — CNAME records supportedTerms require the root name to relate to software development; approval by volunteers (hours–days). Fine for an engineering team's internal tool.
eu.orgA real delegated domain yourname.eu.org you host on free Cloudflare DNS, any records you likeYes — the cleanest free resultApproval is manual and notoriously slow: days if lucky, often months.
DuckDNS, No-IP free, etc.Dynamic-DNS namesNo — A records only, no CNAME; Cloud Run domain mapping needs a CNAME—
Cheap paid (not free)Your own .xyz, .click, .site from Porkbun / Namecheap / Cloudflare RegistrarYes≈ $1–3 first year for the "ugly" TLDs, $10 for .com. Honestly the best value if Path A's address bothers you.

With any of these, set DOMAIN_MODE=custom, WEB_HOST=app.yourname.mooo.com, API_HOST=api.yourname.mooo.com and follow Path B. Cloud Run will also ask you to verify ownership of the parent name in Google Search Console the first time (it offers a TXT record to add — all the services above support TXT).

Never configure

Supabase anon/service_role keys, Supabase Auth, Supabase JWT secret — EST does not use them. Developer endpoints (/api/v1/dev/…) exist only on a developer's laptop profile and are impossible to turn on in prod.

Later: updating, rolling back, rotating

Terminal

Deploy a new version (after pulling the latest code):

infra/deploy/03-build-push.sh && infra/deploy/04-deploy-api.sh && infra/deploy/05-deploy-web.sh && infra/deploy/07-verify.sh

Roll the API back to the previous version (list revisions, then send all traffic to one):

gcloud run revisions list --service est-api --region REGION
gcloud run services update-traffic est-api --region REGION --to-revisions est-api-00012-abc=100

Change the Supabase password or Google client secret: update ~/est-deploy.env, then

infra/deploy/02-secrets.sh && infra/deploy/04-deploy-api.sh

Rotate the login signing keys (everyone is signed out within 15 minutes; calendars stay linked):

ROTATE_KEYS=yes infra/deploy/02-secrets.sh && infra/deploy/04-deploy-api.sh
Rotating est-crypto-key (part of ROTATE_KEYS=yes) makes previously stored calendar access unreadable: every member must re-link their Google account. Do it only if the key may have leaked.

Read logs:

gcloud run services logs read est-api --region REGION --limit 100

What you seeWhy / what to do
Script: ✖ Settings file not foundStep 1 was skipped — copy the template to ~/est-deploy.env.
Script: ✖ … is missing or still a placeholderFill that line in the settings file (no change-me left).
